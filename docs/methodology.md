# RepoRadar 方法论：GitHub 仓库可发现性与 AEO

| 项 | 内容 |
|---|---|
| 文档 | 方法论（规则理论依据） |
| 版本 | v1.0 |
| 日期 | 2026-10-22 |
| 关联 | `docs/DESIGN.md`（实现规格）、`docs/rule-references.md`（规则 ↔ 方法论 ↔ 分值对照） |

本文档回答一个问题：**为什么这 29 条规则、6 个维度就能衡量「一个 GitHub 仓库是否容易被发现」？**

RepoRadar 不预测排名，也不承诺流量。它衡量的是一组**可观测、可复现、可解释的内容准备度信号**；真实曝光必须由外部证据单独验证（见 `M-P2`）。

---

## 1. 三条检索通道（`M-P1`）

一个开源项目被「看到」，实际经过三条相互独立但共享输入信号的通道：

| 通道 | 典型入口 | 主要消费的信号 | 失败表现 |
|---|---|---|---|
| GitHub 原生搜索 | 站内搜索、Topics 页、Explore、依赖推荐 | 仓库名、Description、Topics、主语言、README、活跃度 | 搜关键词不出现在结果里；出现在结果里但摘要不吸引点击 |
| 传统搜索引擎 | Google / Bing | 可抓取的公开页面、Description、README 正文、外链与文档站 | 页面不被收录，或标题/摘要由机器猜测生成 |
| AI 回答引擎（AEO） | ChatGPT / Perplexity / Gemini / Copilot | 语义化正文、结构化事实、示例、限制说明、实体一致性 | 回答里不提及项目，或提及了却讲错用途/技术栈 |

三条通道的共同点：

1. **都从元数据开始**：名称与 Description 是标题与摘要的第一来源；
2. **都依赖 README 语义**：搜索做关键词相关性，AI 做语义理解与事实抽取；
3. **都惩罚不一致**：名称、描述、README、Topics 互相矛盾时，相关性与可信度同时下降。

因此 RepoRadar 的规则不按「平台」拆分，而按**信号类型**拆分：内容（D1）、元数据（D2）、AI 可理解性（D3）、可抓取性（D4）、可信度（D5）、时效性（D6）。同一份信号同时服务三条通道，这是 6 维度模型的理论起点。

## 2. 静态准备度与真实曝光分层（`M-P2`）

必须严格区分两类指标，禁止混算：

| 层 | 含义 | 数据来源 | 是否进入总分 |
|---|---|---|---|
| 静态审计（Readiness） | 内容是否**准备好**被发现与理解 | 仓库 API、README、根文件、Release、Contributor | 是 |
| 外部证据（Visibility Evidence） | 是否**真的**被收录、被提及、被引用 | Google Custom Search API、多模型 AEO 探测 | 否，单独呈现 |

设计铁律：

- 总分回答「还有哪些可修复的准备度问题」，不回答「现在排第几」；
- 外部验证只输出 `已验证 / 未发现证据 / 无法检测` 三态，**「未配置」「不可达」绝不等于「未收录」**；
- 外部证据不得反向修改静态分数，避免「AI 说好就高分」的循环论证。

对应实现：`repo_seo/verify/`（Google 收录核验 + 多模型 AEO 探测），与 `repo_seo/scoring/` 完全解耦。

## 3. 证据驱动与可解释性（`M-P3`）

**只给分数是无效诊断。** 每个检查项必须输出五元组：

```text
检测结果 → 证据位置（文件/行/URL/原文摘录）→ 扣分原因 → 修复建议 → 修复示例
```

理论依据：

- 用户需要的不是「README 18/25」，而是「丢了 7 分，因为首段没说明解决什么问题」；
- 可解释性是**可审计性**的前提：规则结论必须能被人工复核推翻；
- 修复示例把诊断转成行动，降低「知道有问题但不知道怎么改」的转化损耗。

对应实现：`RuleResult(evidence, reason, suggestion, example)`，报告层原样呈现。

## 4. 硬性规则与语义判断分离（`M-P4`）

| 类型 | 判定方式 | 可信度 | 示例 |
|---|---|---|---|
| 硬性（hard） | 程序确定，无歧义 | 确定 | LICENSE 是否存在、Topics 是否为空、CI 文件是否存在、H2 数量 |
| 语义（semantic） | 规则启发式，可人工复核 | 带置信度（0.80–0.90） | 首段是否说清定位、关键词覆盖是否自然、是否夸大 |

约束：

- 语义判断**不得伪装成事实**：报告中标注置信度，保留人工复核入口；
- 语义规则只做「可解释的启发式」，不引入不可复现的模型判断到评分主链路；
- 同一条规则内部允许混合评分（例如 R03 的安装命令 + 代码示例各占一半），但类型必须标注清楚。

这是「确定性评分 + 可选 AI 建议」架构的理论依据：**评分权威来自确定性引擎，AI 只增强建议文本**。

---

## 5. 三状态模型（`M-P5`）

所有检查项输出四种状态：

| 状态 | 含义 | 是否进入分母 | 报告措辞 |
|---|---|---|---|
| `pass` | 通过 | 是 | 通过 |
| `fail` | 未通过 | 是 | 扣分 + 原因 |
| `n_a` | 不适用（如无文档站时的 Sitemap） | 否 | 不适用，不扣分 |
| `unknown` | 无法检测（无授权/数据缺失） | 否 | 无法检测 / 未验证 |

理论依据：

- **不适用 ≠ 做得差**：没有独立文档站的项目不应该因为「没有 sitemap」被扣分；
- **未检测 ≠ 未收录**：没有 Google 授权时，只能诚实地说「无法检测」；
- 剔除分母让分数保持可比性，同时避免「惩罚项目形态差异」。

对应实现：`EvidenceStatus` 枚举 + `scoring/scorer.py` 的动态分母。

---

## 6. 反伪优化（`M-P6`）

评分体系必须抵抗「为提分而做的无价值修改」，否则会奖励作弊而非可发现性：

| 伪优化行为 | 规则如何抵抗 |
|---|---|
| 关键词堆砌 | R02 设置 `max_hits=30`，超限判 fail |
| Topics 越多越好 | M03 检查数量上限 + 与描述语义相关度，无关标签扣分 |
| 空泛吹嘘 | A05 检测「最好/第一/完美/best/#1」等夸大词 |
| 只堆字数不写清定位 | R01 要求首段说明「是什么 + 解决什么」，弱词直接判 fail |
| 用 commit 数冒充活跃 | AC01 只看最近推送时间，且按项目年龄放宽阈值 |

原则：**每条规则都必须能回答「这条修改对真实发现有什么帮助」**；回答不了，就不该加分。

## 7. 六个维度（`M-D1` ~ `M-D6`）

### 7.1 `M-D1` README 内容质量（25 分）

规则：`R01` `R02` `R03` `R04` `R05`

README 是唯一同时被三条通道完整读取的资产：GitHub 搜索索引全文，搜索引擎抓取正文，AI 直接从中抽取事实。因此它权重最高。

它检测的失败模式：

- 首段没说清「是什么、解决什么问题」（R01）；
- 没有关键词锚点，或反过来堆砌关键词（R02）；
- 没有可复制的安装命令与代码示例，用户/AI 无法验证可用性（R03）；
- 标题层级混乱、代码块无语言标注，结构化抽取失败（R04）；
- 没有 FAQ / 使用场景 / 限制说明，失去被 AI 直接引用的高价值段落（R05）。

### 7.2 `M-D2` 仓库元数据（20 分）

规则：`M01` `M02` `M03` `M04` `M05`

元数据是搜索结果的**标题、摘要、分类**来源，也是 AI 判断「这个仓库是做什么的」的第一段输入。它决定「搜得到」与「搜到了愿不愿意点」。

它检测的失败模式：

- 仓库名泛化（my-/demo-/test-）或与领域无关（M01）；
- Description 为空、过长、核心词后置、全中文（M02）；
- Topics 为空、过多、与主题无关（M03）；
- 主语言不可识别，技术栈搜索无法命中（M04）；
- 没有官网/文档/演示入口，少一个信任通道（M05）。

### 7.3 `M-D3` AI 检索准备度 / AEO（20 分）

规则：`A01` `A02` `A03` `A04` `A05`

这是本项目区别于传统 SEO 工具的差异化维度。AI 不是关键词匹配器，它需要：

1. 稳定的实体身份（项目名 + 技术栈）；
2. 明确的适用场景（回答「我要做 X，该用什么」）；
3. 可摘引的具体事实（代码示例、功能清单）；
4. 可解析的结构（标题、列表、表格）；
5. 诚实的边界（限制、兼容性，不夸大）。

对应失败模式：AI 不知道这个项目 → 知道但归错类 → 归类正确但答不出细节 → 答得出但引用错误 → 因夸大而不被信任。

### 7.4 `M-D4` 搜索可发现性（15 分）

规则：`D01` `D02` `D03` `D04` `D05`

这一维度衡量「页面与文档是否具备被抓取的条件」，而不是「是否已经排名」。

它检测的失败模式：

- 仓库私有或已归档，外部完全不可见（D01，私有直接 P0）；
- 没有任何收录证据（D02，静态阶段固定 `unknown`，由 `--verify` 补证）；
- 文档站不可访问或不存在（D03，无文档站记 `n_a`）；
- 文档站缺少 sitemap / 规范 URL 协议（D04，同上）；
- README 没有任何内外部链接，信息通道单一（D05）。

### 7.5 `M-D5` 工程健康与可信度（10 分）

规则：`H01` `H02` `H03` `H04` `H05`

工程健康不直接提升搜索相关性，但它影响**是否被推荐**：AI 与用户都会过滤无 License、无测试、无版本的仓库。

它检测的失败模式：无许可（法律风险）→ 无 CI（未验证）→ 无测试（质量未知）→ 无 Release（未交付）→ 无包元信息（无法安装）。

### 7.6 `M-D6` 项目活跃度（10 分）

规则：`AC01` `AC02` `AC03` `AC04`

活跃度是「项目是否还活着」的代理信号，但**不能简单数 commit**：成熟项目长期稳定并不等于衰败。

设计约束：

- 按仓库年龄动态阈值（创建 <365 天看 90 天，否则看 180 天）；
- `open_issues = 0` 返回 `unknown`，不判断为「无人使用」或「响应迅速」；
- 只衡量维护节奏与协作入口，不把 star 数当质量。

## 8. 评分与优先级

### 8.1 加权模型

```text
维度分 = Σ(该维度启用的检查项实得分)
可评分值 = Σ(启用项分值) − Σ(N/A 项分值) − Σ(UNKNOWN 项分值)
总分 = Σ维度实得分 / Σ可评分值 × 100
```

默认权重：README 25 / 元数据 20 / AEO 20 / 可发现性 15 / 工程健康 10 / 活跃度 10 = 100。

通过 `--config` 禁用规则或覆盖分值时，分母动态变化；此时报告必须标注「已应用自定义规则配置」，**自定义分数不代表官方评分模型**。

### 8.2 优先级

| 级别 | 定义 | 典型场景 |
|---|---|---|
| P0 | 直接阻断可发现性 | 私有仓库、无 README、空 Description、空 Topics |
| P1 | 明显削弱搜索与 AI 引用概率 | 缺 FAQ/AEO 段、无 CI、无 License、活跃度低 |
| P2 | 锦上添花 | 多语言 README、外链、文档站、Sitemap |

报告固定输出 **Top 3 优先修复问题**，每条标注影响维度与预计改善指标，防止用户把精力花在低价值项上。

## 9. 审计流水线

```text
URL / owner-repo
   │
   ▼
URL 解析与校验 ──► GitHub REST API（元数据 / 根文件 / Releases / Contributors）
   │                     │
   │                     ├─ README 降级链：API → raw → 网页（公开仓库）
   │                     ▼
   │                RepoSnapshot（统一快照）
   │                     │
   │                     ▼
   │              规则引擎：6 维度 × 29 条规则
   │                     │
   │                     ├─► RuleResult[]（状态 / 得分 / 证据 / 原因 / 建议）
   │                     ▼
   │              评分器：动态分母 + 维度分 + 总分 + P0/P1/P2 + Top3
   │                     │
   │                     ├─► 报告层：终端 / Markdown / HTML / JSON
   │                     ├─► 建议层：规则模板 + 可选 LLM（永不改分）
   │                     └─► 历史层：追加趋势记录（monitor / trend）
   │
   └─► 外部验证（--verify）：Google 收录核验 + 多模型 AEO 探测
            └─► Search Visibility Evidence（独立呈现，不进入总分）
```

## 10. 已知局限与诚实约束

1. **语义规则是启发式**：R01/R02/R05/A01/A02/A03/A05/M03 依赖关键词、长度、标题结构与置信度标注，不等同于人工评审；结果应允许人工复核。
2. **D02 在静态引擎中恒为 `unknown`**：无外部授权时无法核验收录；只有 `--verify`（Google Custom Search API）能给出 `indexed / not_indexed / unknown`。
3. **D05 只检查链接“存在”**：README 中出现 http(s) 链接即通过，未做 HTTP 可达性与 404 核验。
4. **活跃度不是质量**：阈值只反映维护节奏，成熟项目的低频发布不会被惩罚，但也不会因此获得额外加分。
5. **无法观测的指标**：stars、backlinks、真实流量、搜索排名、AI 回答中的实际引用率，均不在静态审计能力范围内。
6. **未来扩展（明确未纳入当前评分）**：批量仓库矩阵对比、更多原生 AEO 服务商（Gemini / Perplexity / Claude 等）、长期趋势告警、PyPI 正式发布；这些不影响当前 29 条规则的结论。
